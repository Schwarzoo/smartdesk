# SmartDesk

SmartDesk is a table booking system for shared study or work spaces. It combines a React web application with a small Node.js/Express REST server that stores reservations and exposes the APIs needed by the frontend and by future ESP32 devices installed on each table.

The intended physical setup is a table device based on ESP32 with a presence sensor, LEDs, display, and optional NFC reader. The web app lets users reserve a table, while the device can use the server API to understand whether its table is currently booked, show the reservation status locally, and eventually report real physical presence or direct bookings made from the table.

## Main Features

- Interactive map of six tables, loaded from `smartdesk/src/data/tavoli.json`.
- Visual distinction between free and occupied tables.
- Reservation popup with a two-day calendar view.
- 15-minute booking slots from 08:00 to 22:00.
- Reservation overlap validation on both frontend and backend.
- Automatic frontend refresh of table reservations every 60 seconds.
- Backend cleanup of expired reservations at startup and then once per hour.
- JSON-file persistence for simple local and Fly.io deployment.
- REST API that can be consumed by the React frontend and ESP32 table devices.

## Architecture

```text
React frontend
    |
    | HTTP/JSON
    v
Express REST server
    |
    | reads/writes
    v
tavoli.json
```

In production, the frontend is expected to run as a static React build, for example on Vercel. The server is configured for Fly.io and stores data in a persistent volume mounted at `/data`.

When the server runs locally, it stores reservations in:

```text
server/tavoli.json
```

When the server runs on Fly.io, it stores reservations in:

```text
/data/tavoli.json
```

The server decides which path to use through the `FLY_APP_NAME` environment variable.

### Get All Tables and Reservations

```http
GET /api/tavoli
```

Returns all tables known by the server and their reservations.

Example response:

```json
[
  {
    "id": 1,
    "reservations": [
      {
        "id": 1765881951589,
        "nome": "Andrea",
        "oraInizio": 1765872000,
        "oraFine": 1765875600
      }
    ]
  }
]
```

Field meaning:

| Field | Type | Description |
| --- | --- | --- |
| `id` | number | Table identifier. The frontend layout currently uses table IDs from `1` to `6`. |
| `reservations` | array | Reservations for that table. |
| `reservations[].id` | number | Reservation identifier generated by the backend with `Date.now()`. |
| `reservations[].nome` | string | Name attached to the reservation. |
| `reservations[].oraInizio` | number | Reservation start time as Unix epoch seconds. |
| `reservations[].oraFine` | number | Reservation end time as Unix epoch seconds. |

The frontend uses this endpoint to:

- Mark a table as occupied when the current time is inside one of its reservations.
- Display unavailable time ranges inside the reservation popup.
- Refresh the map every 60 seconds.

An ESP32 table device can also call this endpoint to find the current reservation for its own table and update LEDs or display text.

Example:

```bash
curl http://localhost:8080/api/tavoli
```

### Create a Reservation

```http
POST /api/prenotazioni
```

Creates a new reservation for a table.

Request body:

```json
{
  "id": 1,
  "nome": "Andrea",
  "oraInizio": 1765872000,
  "oraFine": 1765875600
}
```

Validation rules:

- `id`, `nome`, `oraInizio`, and `oraFine` are required.
- `oraInizio` and `oraFine` must be valid numbers.
- `oraInizio` must be lower than `oraFine`.
- `oraInizio` cannot be in the past.
- The requested interval must not overlap an existing reservation for the same table.

Successful response:

```http
201 Created
```

```json
{
  "id": 1765881951589,
  "nome": "Andrea",
  "oraInizio": 1765872000,
  "oraFine": 1765875600
}
```

Possible error responses:

| Status | Body | Meaning |
| --- | --- | --- |
| `400` | `{ "error": "Dati mancanti" }` | Missing required fields. |
| `400` | `{ "error": "Intervallo orario non valido" }` | Invalid time range. |
| `400` | `{ "error": "Non puoi prenotare in un periodo precedente a quello attuale" }` | Start time is in the past. |
| `409` | `{ "error": "Orario non disponibile" }` | The requested interval overlaps another reservation. |
| `500` | `{ "error": "Errore salvataggio prenotazione" }` | Server-side write error. |

Example:

```bash
curl -X POST http://localhost:8080/api/prenotazioni \
  -H "Content-Type: application/json" \
  -d '{"id":1,"nome":"Andrea","oraInizio":1765872000,"oraFine":1765875600}'
```

The ESP32 can use this endpoint for a booking flow started directly from the physical table, for example after reading a student card through NFC and letting the user select a time range on the device.

### Delete a Reservation

```http
DELETE /api/prenotazioni/:id
```

Deletes one reservation by reservation ID. The backend searches all tables and removes the first matching reservation.

Successful response:

```json
{
  "message": "Prenotazione eliminata"
}
```

Possible error responses:

| Status | Body | Meaning |
| --- | --- | --- |
| `404` | `{ "error": "Prenotazione non trovata" }` | No reservation with that ID exists. |
| `500` | `{ "error": "Errore eliminazione prenotazione" }` | Server-side delete error. |

Example:

```bash
curl -X DELETE http://localhost:8080/api/prenotazioni/1765881951589
```

The ESP32 could use this endpoint to release a reservation when the physical no-show policy decides that the booked user did not arrive. In the current implementation this is a direct deletion, so use it carefully.

## Data Model

The backend persistence file stores an array of table records:

```json
[
  {
    "id": 1,
    "reservations": [
      {
        "id": 1765881951589,
        "nome": "Andrea",
        "oraInizio": 1765872000,
        "oraFine": 1765875600
      }
    ]
  }
]
```

Important details:

- Time values are Unix epoch seconds.
- The UI formats dates and times for the Italian locale.
- Expired reservations are removed when `oraFine <= now`.
- The local frontend table layout is separate from backend reservation storage:
  - `smartdesk/src/data/tavoli.json` defines table positions on the map.
  - `server/tavoli.json` stores reservation data.

## Frontend Behavior

The main frontend flow is:

1. The user opens the SmartDesk web app.
2. The `Mappa` component loads the static table layout from `src/data/tavoli.json`.
3. The frontend calls `GET /api/tavoli` through `src/utils/apiService.js`.
4. Each table is marked as occupied when the current timestamp is between `oraInizio` and `oraFine`.
5. The user clicks a table and opens `PopupPrenotazione`.
6. The popup fetches reservations for that table and displays today and tomorrow.
7. The user selects contiguous free 15-minute slots.
8. The frontend calls `POST /api/prenotazioni`.
9. The backend validates the interval and saves the reservation.

The popup also contains an "Elimina prenotazioni" button. It currently deletes all reservations by loading all tables and calling `DELETE /api/prenotazioni/:id` for each reservation.

## ESP32 Integration Notes

The current backend already exposes enough API surface for an ESP32 device to:

- Read current and upcoming reservations with `GET /api/tavoli`.
- Find the reservation list for the table assigned to that specific device.
- Show the current reservation name and time range on a local display.
- Drive LEDs according to whether the table is free, reserved, or currently occupied by time.
- Create a reservation from the table device with `POST /api/prenotazioni`.
- Cancel or release a reservation with `DELETE /api/prenotazioni/:id`.

Suggested ESP32 polling flow:

```text
1. Store the physical table ID in the ESP32 firmware.
2. Periodically call GET /api/tavoli.
3. Select the table object whose id matches the device table ID.
4. Compare current Unix time with each reservation interval.
5. If now is inside a reservation:
   - show the reservation name on the display
   - set the table status to reserved or occupied
   - update LEDs according to remaining or elapsed time
6. If no reservation is active:
   - show "Table free"
   - set LEDs to the free state
7. If NFC booking is supported:
   - collect user identity and selected time range
   - call POST /api/prenotazioni
```

The current `server.js` does not yet implement a dedicated endpoint for real-time physical presence events from the ESP32. If the project needs the hardware to explicitly report sensor state, the following API additions would be useful:

```http
POST /api/tavoli/:id/presence
```

Example body:

```json
{
  "occupied": true,
  "timestamp": 1765872100,
  "reservationId": 1765881951589,
  "source": "esp32-presence-sensor"
}
```

Possible use:

- Store whether a person is physically seated at a table.
- Confirm that a reservation has actually been used.
- Release a reservation after a no-show timeout.

```http
GET /api/tavoli/:id/status
```

Possible use:

- Return a compact device-specific state for one table.
- Avoid making each ESP32 download all table reservations.

Example response:

```json
{
  "id": 1,
  "status": "occupied",
  "currentReservation": {
    "id": 1765881951589,
    "nome": "Andrea",
    "oraInizio": 1765872000,
    "oraFine": 1765875600
  },
  "presence": {
    "occupied": true,
    "lastSeen": 1765872100
  }
}
```

```http
PATCH /api/prenotazioni/:id/check-in
```

Possible use:

- Mark a reservation as confirmed when the ESP32 detects the booked user at the table.

These endpoints are not implemented yet. They are documented here as recommended extensions for the hardware integration phase.

## Known Limitations

- There is no authentication or authorization yet.
- Any client that can reach the backend can create or delete reservations.
- Reservation storage is a JSON file, which is simple but not ideal for concurrent writes or high traffic.
- The backend does not yet store physical presence state from ESP32 devices.
- There is no per-table compact status endpoint yet.
- Reservation IDs are generated with `Date.now()`, which is sufficient for this prototype but not ideal for distributed systems.
- The current `POST /api/prenotazioni` validation treats falsy table IDs as missing, so table IDs should start from `1`.

## Suggested Next Steps

- Add authentication for admin actions and hardware devices.
- Add a device token or API key for ESP32 requests.
- Implement ESP32 presence/status endpoints.
- Move persistence from JSON files to a small database if concurrent use grows.
- Add automated backend tests for reservation overlap, cleanup, and deletion.
- Add end-to-end tests for the frontend booking flow.
